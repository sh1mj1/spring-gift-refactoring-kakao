# 인수 테스트 작성

## 입력

- 필수: 사용자 스토리 문서 경로와 대상 스토리. 대상은 행의 제목이나 설명으로 지정하며, 문서 전체를 요청하면 모든 스토리를 대상으로 한다.
- 선택: 관찰 기록이나 확인 필요 목록의 경로, 모범 테스트 경로, 이번 작업에서 제외할 시나리오.

## 초안과 승인

1. 스토리, 제공된 관찰 기록, 기존 테스트와 구현을 대조한다. 이미 검증하는 시나리오는 표시하고 중복 작성을 피한다. 관찰 기록이 불충분하면 허용된 로컬 환경의 정상 HTTP 진입점에서 확인한다. 상태를 바꾸는 요청에는 격리된 테스트 데이터를 쓴다. 확인이 불가능하거나 스토리에서 제외한 시나리오는 초안에 보류 이유를 명시한다.
2. 시나리오별로 주어진 상태, 입력 또는 요청, 기대 결과를 표로 보여준다. 사용자 목표별 Feature와 Given/When/Then 시나리오 초안을 함께 제시한다. 상태 코드, 의미 있는 본문과 헤더, 변경이나 실패 뒤의 후속 조회 결과를 구체적으로 적는다. 확인된 비정상 동작도 현재 결과를 기준으로 명시한다.
3. 초안이 승인될 때까지 테스트나 설정을 수정하지 않는다. 승인 후에는 테스트 작성과 실행까지 진행한다. 구현 중 관찰된 결과 때문에 승인된 인수 조건이 달라져야 하면 차이를 설명하고 그 조건에 대한 승인을 다시 받는다.

## 테스트와 결과

- 모범 테스트와 프로젝트 지침을 읽고 기존 테스트 도구와 스타일을 재사용한다. 테스트 실행에 필요한 설정이나 의존성이 있다면 초안에 각 변경 줄과 이유를 넣어 함께 승인받는다. 승인 뒤에 필요해진 경우에는 해당 변경만 별도로 승인받는다.
- 목록과 상세 조회처럼 각각 결과를 갖는 행동은 테스트를 나눈다. 표시 이름은 주어진 상황과 행동, 기대 결과가 읽히는 자연스러운 문장으로 쓰고 Given/When/Then은 본문 주석에 사용한다. 준비가 요청 자체에 포함되면 `// given & when`을 쓴다.
- 각 테스트의 선행 상태를 독립적으로 준비하고 정상 진입점으로 요청한다. 상태 코드와 의미 있는 응답 값을 확인한다. 상태 변경과 실패의 영향은 후속 요청으로 검증한다.
- 변경 범위는 테스트와 명시적으로 승인받은 테스트 실행 설정으로 제한한다. 프로덕션 코드와 동작을 유지하고 확인된 버그는 관찰된 결과대로 단언한다.
- 대상 테스트를 실행한다. 테스트나 환경 문제는 승인된 인수 조건을 유지하며 해결하고 재실행한다. 실제 동작이 조건과 다르면 재승인을 요청한다. 모두 통과했거나 해결할 수 없는 차단 원인이 확인되면 실행 명령, 출력 요약, 통과 또는 실패 수와 남은 차단 원인을 공유한다.
